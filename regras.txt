IV.1 Summary
You will implement a maze generator in Python that takes a configuration file, generates
a maze, possibly perfect (with a single path between entrance and exit), and writes it to a
file using a hexadecimal wall representation. You will also provide a visual representation
of the maze and organize your code so that the generation logic can be reused later.
IV.2 Usage
Your program must be run with the following command:
python3 a_maze_ing.py config.txt
• a_maze_ing.py is your main program file. You must use this name.
• config.txt is the only argument. It is a plain text file that defines the maze
generation options. You can use a different filename.
Your program must handle all errors gracefully: invalid configuration, file not found, bad
syntax, impossible maze parameters, etc. It must never crash unexpectedly, and must
always provide a clear error message to the user.
IV.3 Configuration file format

Lines starting with # are comments and must be ignored.

IV.4 Maze Requirements
• The maze must be randomly generated, but reproducibility via a seed is required.
• Each cell of the maze has between 0 and 4 walls, at each cardinal point (North,
East, South, West).
• The maze must be valid, meaning:
◦ Entry and exit exist and are different, inside the maze bounds.
◦ The structure ensures full connectivity and no isolated cells (except the ’42’
pattern, see below).
◦ As entry and exit are specific cells, there must be walls at the external borders.
◦ Your generated data must be coherent: each neighbouring cell must have the
same wall if any. E.g., it is forbidden to have a first cell with a wall on the
east side, and the second cell behind that wall without a wall on the west side.
• The maze can’t have large open areas. Corridors can’t be wider than 2 cells.
For example, you can have 2x3 or 3x2 open area, but never a 3x3 open area.
• When visually represented (see below), the maze must contain a visible “42” drawn
by several fully closed cells.
• If the PERFECT flag is activated, the maze must contain exactly one path between
the entry and the exit (i.e., it must be a perfect maze: no loops at all).
• If the PERFECT flag is not activated (the default), the maze must instead be a board
directly usable by a Pac-Man-like game. Concretely:
◦ every corridor is reachable (full connectivity), so the whole board can be filled
with pac-gums and remains winnable;
◦ the four corners and the centre are open corridors (the ghosts and super-pacgums sit in the corners, the player starts in the centre);
◦ it offers at least two independent routes (loops), so that a chased player
always has an alternative (a perfect maze, or a perfect maze with merely one
wall removed (a single loop), is therefore not acceptable in this mode);
◦ dead-ends should stay rare (a couple are tolerated); a board with no dead-end
at all is the ideal and is rewarded as a bonus (see the Bonuses chapter).
The “42” pattern may be omitted in case the maze size does not allow
it (i.e. too small). Print an error message on the console in that
case

IV.5 Output File Format
The maze must be written in the output file using one hexadecimal digit per cell, where
each digit encodes which walls are closed:
Bit Direction
0 (LSB) North
1 East
2 South
3 West
• A wall being closed sets the bit to 1, open means 0.
Example: 3 (binary 0011) means walls are open to the south and west. Or A
(binary 1010) means that east and west walls are closed.
• Cells are stored row by row, one row per line.
• After an empty line, the following 3 elements are inserted in the output file on 3
lines:
◦ the entry coordinates, the exit coordinates, and the shortest valid path from
entry to exit, using the four letters N , E , S , W .
• All lines end with a \n .

2. EXECUÇÃO OBRIGATÓRIA
-----------------------

O programa deve ser executado com:

	python3 a_maze_ing.py config.txt

Requisitos:

- a_maze_ing.py deve ser o arquivo principal;
- config.txt é o único argumento;
- erros de arquivo, sintaxe, configuração e parâmetros impossíveis devem ser
  tratados com mensagens claras;
- o programa não deve quebrar inesperadamente.


3. FORMATO DA CONFIGURAÇÃO
--------------------------

Cada linha válida tem o formato KEY=VALUE. Linhas vazias e linhas iniciadas
com # devem ser ignoradas.

Chaves obrigatórias:

	WIDTH=20
	HEIGHT=15
	ENTRY=0,0
	EXIT=19,14
	OUTPUT_FILE=maze.txt
	PERFECT=True

Chaves adicionais, como SEED, são permitidas. Deve existir uma configuração
default versionada no repositório.


4. REQUISITOS DO LABIRINTO
--------------------------

O labirinto deve:

- ser aleatório e reproduzível quando uma seed for usada;
- ter células com paredes Norte, Leste, Sul e Oeste;
- manter ENTRY e EXIT dentro dos limites e em posições diferentes;
- ser totalmente conectado, sem células isoladas;
- manter as bordas externas fechadas;
- manter paredes compartilhadas coerentes entre células vizinhas;
- não criar áreas abertas maiores que 2 células de largura;
- conter um padrão visual 42 quando o tamanho permitir;
- informar no console quando o padrão 42 não puder ser criado.

Modo PERFECT=True:

- deve existir exatamente um caminho entre entrada e saída;
- não pode haver loops.

Modo PERFECT=False:

- todos os corredores devem ser alcançáveis;
- os quatro cantos e o centro devem ser corredores abertos;
- devem existir pelo menos dois caminhos independentes;
- becos sem saída devem ser raros.


5. FORMATO DO ARQUIVO DE SAÍDA
------------------------------

Cada célula ocupa um dígito hexadecimal. Os bits representam paredes fechadas:

	bit 0 (1): Norte
	bit 1 (2): Leste
	bit 2 (4): Sul
	bit 3 (8): Oeste

Parede fechada = bit 1. Passagem aberta = bit 0.

As células são escritas linha por linha. Depois das linhas do labirinto, o
arquivo deve conter:

1. uma linha vazia;
2. as coordenadas da entrada;
3. as coordenadas da saída;
4. o caminho mínimo usando N, E, S e W.

Todas as linhas devem terminar com \n.


6. VISUALIZAÇÃO E INTERAÇÕES
----------------------------

Deve existir uma visualização ASCII ou MiniLibX que mostre:

- paredes;
- entrada;
- saída;
- caminho da solução.

Durante a execução, deve ser possível:

- gerar e exibir outro labirinto;
- mostrar ou ocultar o caminho mínimo;
- alterar a cor das paredes;
- opcionalmente destacar o padrão 42.
